## 重要な発見 (本セッション)

### A. CI workflow trigger filter の盲点

`python-tests.yml` は `branches: [develop, master]` で `pull_request` をフィルタしていたが, fork 上の事実上の main line である `chore/pre-push-hook-worktree-compat` がそこに無かったため, **PR #178-#183 はすべて GitHub Actions が動いていなかった**. handoff で「Bugbot 'no new issues'」と書かれていた成果は Cursor Bugbot (cursor.com) の review のみ. PR #184 で `chore/...` を filter に追加して修復.

### B. `tot_api_check_all` は CI に未配線だった

L-6 plan で test_smoke / test_param / test_negative / test_full_cycle は Makefile target としては存在したが, **どの workflow にも実走 step が無かった**. PR #185 で初めて CI に配線, **どのプラットフォームでも end-to-end 実走実績ゼロ** だった事実を示した. 結果 test_smoke.c に L-3 stub 期待のままの assertion が残存していたことも発見.

### C. graphics stub の per-module vs orchestrator の使い分け

- `*/×_graphics_stubs.f90` (per-module, 既存): 各モジュールの `.so` build 時に link. PIC chain 専用, 7-57 stubs.
- `tot/tot_static_stubs.f90` (新規, PR #185): orchestrator-level union 102 stubs. 静的リンク C driver + `tot` 実行ファイルに link, GFLIBS empty で gated.
- 両者は**異なる link path で link** されるので symbol 重複しない. `tot/tot_graphics_stubs.f90` (既存 7 stubs, libtotapi.so 専用 minimal safety net) も別物として共存.

### D. macOS local build env の保守手順

graphics lib (`libg3d-gfc64`) が macOS に無いため, `make -C tot tot GFLIBS=""` のように **明示的に GFLIBS を空にする** override が必須. 通常の `make.header` の GFLIBS は graphics ref を持つが, それらの実体は macOS には存在しない (CI 用 Linux Docker でのみ存在).

非-PIC chain build (本セッション 1 度実行): `mtxp clean && make -C mtxp` → `pl clean && make -C eq` (eq が pl chain を triggerする) → `make -C tot libs` で全ての非-PIC `.a` build → 各モジュールの API .o (`make -C eq eq_api_compile_check`, `make -C tr tr_api_check`, etc.) → `make -C tot tot_api_check_all GFLIBS=""`. PR #185 + #186 の Makefile fix で必要な明示依存が増えたため, 今後は `make -C tot tot_api_check_all GFLIBS=""` 一発で bootstrap 可能 (Makefile 内で `make -C tot libs` 相当を chain しないので, 順序は workflow 側で `libs` 先行が現状の運用).

### E. ht6m fixture と standalone tot driver の divergence

`test_tot_ht6m_short` が rc=3 (CALCULATION_FAILED) で失敗する原因は **PP0 ではない**. fixture の `tot_ht6m_params.py` は `tot_ht6m_short.eqparm` + `.trparm` を mirror しているはずだが, Python pipeline で再現すると Fortran standalone と挙動が乖離する. 詳細未調査. 関連:
- `eq:PP0` は registry 既存 (eq_param_registry.f90:118) — 元 fixture コメントが stale
- 単純に PP0 を `SCALARS` に足しても rc=3 は解消されない
- 元 input file (`tot_ht6m_short.in`) は `eq` → `r` (read namelist) → `s` → ... と menu commands 経由で読む構造で, `KNAMEQ` の出力ファイル名も Fortran 側 default `eqdata` になり Python 期待値の `eqdata-HT6M` と不一致
